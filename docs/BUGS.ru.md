# AIOS: Известные баги и обходные пути

## RESOLVED (v2.42.0): нативный браузер паниковал при live-загрузке — EventLoop winit в фоновом потоке

- **Статус:** RESOLVED в v2.42.0.
- **Причина:** `WebBrowser::open` строит winit `EventLoop` в рабочем
  потоке `aios-webview`; winit 0.30.13 считает это угрозой
  кросс-платформенной совместимости и паникует на
  `platform_impl/linux/mod.rs:725` («Initializing the event loop outside
  of the main thread …»). Паника убивала только поток webview — TUI
  продолжал работать, и отказ был тихим (процесс WebKit так и не
  появлялся). Вторая усугубляющая причина: в headless live-буте в
  окружении нет `DISPLAY`/`XDG_RUNTIME_DIR`, поэтому даже разрешённый
  цикл не смог бы показать окно.
- **Симптом:** после нажатия `B` на веб-табе ничего не открывается; в
  serial-логе сообщение `thread 'aios-webview' … panicked` и нет
  процессов WebKit/GTK.
- **Фикс:** включён `EventLoopBuilderExtX11::with_any_thread(true)` на
  Linux и подсев `DISPLAY=:0`, `XDG_RUNTIME_DIR=/run`,
  `AIOS_DATA_DIR=/tmp/aios-webview` (записываемый tmpfs) до коннекта
  цикла.
- **Риск:** запуск цикла winit вне главного потока может сказываться на
  фокусе/райзе окна в X11; приемлемо для одноконного браузера,
  управляемого из TUI. Пересмотреть при добавлении многооконного GUI.

## RESOLVED (v2.41.0): Live ISO грузился до чёрного экрана / kernel panic — динамический /init в initramfs без загрузчика

- **Статус:** RESOLVED в v2.41.0.
- **Причина:** `aios-init` (PID 1) и `aios-core.static` были собраны
  динамически: `readelf` показывал `PT_INTERP /lib/ld-musl-x86_64.so.1`.
  В initramfs намеренно только статические бинарники (busybox.static) и
  нет загрузчика ld-musl, поэтому `execve("/init")` падал с ENOENT, и
  ядро паниковало до отрисовки TUI (в QEMU — стабильный тёмный экран;
  serial-лог обрывался на GRUB). Каждый артефакт live до этого был
  незагружаемым.
- **Фикс:** `live/build.sh` собирает `aios-init` и статический фолбэк с
  `-C target-feature=+crt-static` и прерывает сборку, если путь
  интерпретатора `ld-musl` найден в любом из бинарников.
- **Обходной путь (legacy):** загрузка с `init=/bin/sh` из initramfs
  по-прежнему работает, потому что busybox полностью статичен.
- **Риск:** остаточных рисков нет; FATAL-проверка служит регрессионным
  барьером для инварианта «статичный PID 1 + initramfs без загрузчика».

# AIOS: Известные баги и обходные пути

## OPEN (v2.40.0): у встроенного JS-движка всё нет загрузчика модулей / сети из JS / событий ввода (документированные границы)

- **Статус:** OPEN (известные ограничения, выводятся пользователю — каждое
  ограничение в рантайме приходит заметкой в `console`; это не регрессии,
  а осознанные границы объёма). v2.40.0 закрыл lifecycle/динамические
  скрипты/навигацию из прежней записи (см. RESOLVED ниже).
- **Симптом:** страницы, опирающиеся на ES-модули
  (`<script type="module">`), `document.write` или загрузку данных через
  `fetch`/XHR, отрисовывают только статический HTML — скриптовая половина
  пропускается или деградирует. Настоящего event loop по-прежнему нет:
  события пользовательского ввода (click, keydown, ...) никогда не
  рассылаются, потому что текстовый браузер их не порождает; события
  `error`, зарегистрированные через слушателей, хранятся и срабатывают
  только если код страницы сам вызовет `dispatchEvent`. Синтетические
  `DOMContentLoaded`/`load` и ручной `dispatchEvent` РАБОТАЮТ (v2.40.0).
- **Обоснование дизайна:** движок выполняет каждую страницу в свежем
  одноразовом `boa_engine::Context` (мост JSON-in / `JSON.stringify`-out,
  ноль host-функций), сбрасывает таймеры ровно один раз после
  `DOMContentLoaded` и рассылает `load` один раз перед чтением обратно —
  детерминированное post-load состояние для текстового рендера важнее
  частично реализованного event loop. Сеть остаётся в Rust (`reqwest`),
  поэтому `fetch` не может обойти конфиг/таймауты блока.
- **Обход:** страницам, которым нужны эти возможности, открывайте `B`/`n`
  (полноценное нативное окно WebView), либо headless-fallback Chromium
  отрендерит JS-оболочки, когда он доступен.
- **Далее:** кандидаты по приоритету — `<script type="module">` через
  загрузчик модулей boa, host-backed `fetch`/XHR через `NetworkClient`,
  затем (если потребуется) событийный диспатч по таймерам для ввода.

## RESOLVED (v2.40.0): события жизненного цикла, динамические <script> и навигация не срабатывали/не исполнялись/не выполнялись

- **Статус:** RESOLVED в v2.40.0.
- **Симптом (v2.39.0):** обработчики `addEventListener` сохраняются, но
  никогда не срабатывали (`DOMContentLoaded`/`load` не приходили,
  `readyState` навсегда оставался `"complete"`), элементы `<script>`,
  созданные кодом страницы, молча пропускались, а `location.href = ...`
  и `<meta http-equiv="refresh">` печатали
  `[js] navigation ... requested (not followed)` вместо загрузки цели.
- **Исправление:**
  1. Единое ядро диспетчеризации (`fireAt` + `__aiosFire`) в прелоаде
     рассылает `readystatechange`/`DOMContentLoaded` на документ и
     `readystatechange`/`load` на окно+документ в нужных точках
     конвейера страницы; свойства `on<type>` участвуют как обработчики;
     `Event`/`CustomEvent` + `dispatchEvent` теперь работают на каждом
     узле.
  2. `__aiosMarkScripts` предварительно помечает скрипты из парсера;
     раунды обнаружения `__aiosCollectScripts` (8 раундов / 20 скриптов,
     общие для всех фаз жизненного цикла) исполняют инлайн- и `src`-скрипты,
     созданные страницей (`src` грузится через `NetworkClient`).
  3. `build_page` выполняет навигацию из скриптов и meta refresh с нулевой
     задержкой через hop-лимитированный цикл (`MAX_NAV_HOPS = 5`) с
     `[nav]`-трассировками и защитами (same-URL, не-http схема, ошибка
     загрузки); `Page::url` — финальный URL цепочки.
- **Верификация:** 23 новых теста (в crate — 102, workspace зелёный),
  включая end-to-end цепочки против локального HTTP тест-сервера;
  `document.readyState` проходит `loading → interactive → complete` с
  доказательствами в консоли.

## РЕШЕНО (v2.38.40): таблица USB HID-кодов теряла F-клавиши/цифровой блок и искажала пунктуацию (сценарий K красный на каждом ISO)

- **Статус:** РЕШЕНО в v2.38.40 — `usage_to_scancode` расширена и
  исправлена, неотображённые коды логируются под `DEBUG_MODE`; харнесс
  `kp_plus` → `kp_add`.
- **Симптом:** сценарий K (проба маршрутизации клавиатуры при подключённом
  usb-kbd) проваливал все три проверки на каждом ISO с момента появления
  пробы — `key scancode 0x41`, `usb key scancode`, `key scancode 0x4e`,
  всегда «идентично на baseline». Та же дыра в таблице портила живой ввод:
  поле IP Network получало `10,0,2,15` вместо `10.0.2.15` у J (каждая `.`
  превращалась в `,`).
- **Первопричины:**
  1. При подключённом usb-kbd HMP `sendkey` QEMU доходит до гостя только по
     USB HID — PS/2 i8042 не получает ничего (проверено отключением USB:
     `key scancode 0x41` появляется сразу). Каждая клавиша обязана пройти
     через `usage_to_scancode`, но таблица покрывала только
     буквы/цифры/базовую пунктуацию: F1–F12 (`0x3A..=0x45`), клавиши
     блокировки и цифровой блок (`0x54..=0x63`) возвращали `None`, и нажатие
     отбрасывалось без строки лога.
  2. Хвост пунктуации был смещён на один HID-слот от `0x30` (слот `0x2F`
     отсутствовал): `0x30..0x39` отображались с опозданием на слот —
     `.` → `,`, `/` → `.`, CapsLock → `/`, …
  3. В `scancode_to_char` (PS/2-сторона) отсутствовал set-1 `0x29` (grave),
     а `0x2B` отображался в grave/tilde вместо `\`/`|`.
  4. Харнесс слал `sendkey kp_plus`; имя клавиши в QEMU — `kp_add`
     (монитор принимает `kp_plus` без ошибки и ничего не доставляет).
- **Фикс:** исправлена и расширена `usage_to_scancode` (F1–F12,
  Caps/Scroll/Num, операции/цифры/точка цифрового блока через новую таблицу
  `KP_SCANS`; E0-расширенные клавиши остаются неотображёнными — параллельно
  с отбросом `0xE0` в PS/2), исправлены `scancode_to_char` `0x29`/`0x2B`,
  `harvest_report` теперь пишет `[xhci] usb key usage 0xNN unmapped` под F8
  `DEBUG_MODE` вместо молчаливого отбрасывания; харнесс использует `kp_add`.
- **Верификация:** K 3/3 PASS (первый зелёный прогон за всё время) с
  доказательством в serial `usb key scancode 0x41` ×3 +
  `usb key scancode 0x4e`; строки печати J содержат `type '.'` (настоящие
  точки); 11/12 смоуков зелёные на релизном ISO.

## РЕШЕНО (v2.38.35): прыжок указателя — курсор телепортируется через рабочий стол на панель задач (пакеты переполнения + неограниченный backlog)
- **Статус:** РЕШЕНО в v2.38.35 — отбрасывание пакетов с битами
  переполнения i8042 целиком в `ps2::decode_packet`, кламп
  `MOUSE_MAX_STEP = 256` px на ось с carry-over в аккумуляторе в обоих
  драйверах мыши и сливы каждую итерацию в обеих полосах ввода
  idle-цикла.
- **Симптом:** после тяжёлой GUI-операции (клик выбора окна на панели
  задач, переключение вкладки) указатель прыгал на сотни пикселей одним
  отчётом — как правило, садясь на панель задач, где следующее нажатие
  попадало в кнопку окна вместо задуманного виджета; на PS/2-тачпаде
  проявлялось ещё и внезапным прижатием в угол (runaway-гейт v2.38.33
  глушил *поток*, но никогда — единичный прыжок).
- **Причины:**
  1. `ps2::decode_packet` не проверял биты статуса пакета i8042:
     `b0 & 0xC0 != 0` означает, что контроллер уже отбросил это
     движение — перекрученные знаковые dx/dy декодировались как реальный
     шаг в сотни пикселей, а пакет всё равно поднимал `MOUSE_SEQ` и
     публиковал свой nibble кнопки.
  2. Читатели «накопление-и-слив» (`ps2::mouse_dx`/`mouse_dy`,
     `xhci::take_mouse_delta`) выгружали весь аккумулятор только при
     свежей смене счётчика, и ничто не ограничивало величину: backlog,
     накопленный за остановку на полный repaint, выдавался одной дельтой
     со следующим отчётом.
- **Фикс:** пакеты переполнения отбрасываются целиком (без побочных
  эффектов seq/кнопок); одно применение клампится до 256 px на ось с
  парковкой остатка в аккумуляторе (`ps2::drain_axis`, clamp-closure в
  `xhci::take_mouse_delta`); обе полосы сливаются каждую итерацию
  idle-цикла, так что carry-over применяется без ожидания нового ввода;
  счётчик последовательности остался только edge'ом смены кнопки
  (`btn_changed = seq_changed && buttons != last`).
- **Проверка:** смоук D на релизном ISO — строка доказательства клика по
  глобусу и пиксельная проба тела окна, PS/2 строки ограничены
  (`[serial] ps2 mouse id=0x00 … dx=116 dy=0`, чистые пары
  press/release); A ×2, B, C и новый E зелёные на том же ISO, PANIC 0.

## РЕШЕНО (v2.38.37): ~37 с столбняк перед первым USB-клавишным событием (диагностический EP0-пробник внутри `xhci::poll`)
- **Статус:** РЕШЕНО в v2.38.37 — весь путь `probe_hid_state` (`PROBE_EVERY`,
  `PROBE_POLLS`, сама функция) удалён из `xhci::poll`.
- **Симптом:** сценарий M (`Cmd-Latency`/`Type-Keys`) показывал 37 с (и
  3.3 с на повторном ударе), прежде чем ложился паттерн; новая
  инструментация `stage_check` печатала `[serial] [stall] stage xhci took
  23941 ticks`, а пробник — `[xhci] probe ep0 GET_REPORT dt=23941 ticks
  ok=false` — в том же wall-окне.
- **Причина:** каждая 40-я итерация `xhci::poll` выдавала диагностический
  EP0-перенос HID `GET_REPORT`. QEMU никогда не завершал его, поэтому
  `ep0_wait` крутил полный `SPIN_LIMIT` (200 млн итераций ≈ 38 wall-секунд)
  *внутри главного цикла*, дважды за прогон — при подъёме контроллера и
  снова после переполнения счётчика пробника. Всё остальное (рендер, PS/2,
  тики) выстраивалось за ним.
- **Фикс/проверка:** пробник удалён; латентность M 37 с → 0.2 с, строк
  `[stall]` нет; H (37/37), I (8/8), J (9/9) зелёные на том же ISO.
  `stage_check` оставлен постоянным watchdog'ом (порог 2 × TIMER_HZ).

## РЕШЕНО (v2.38.37): USB-клавиатура/мышь умирали ровно после 31 события (link TRB записан с *новым* lap-циклом)
- **Статус:** РЕШЕНО в v2.38.37 — `set_link_cycle` перенесён *до* инверсии
  `cycle = !cycle` во всех четырёх wrap-местах (`arm_ep1`, `arm_ep1_m`,
  `push_ep0`, `cmd_run`).
- **Симптом:** J2 (`Type-Keys` после `Send-Bs`) воспроизводимо умирал
  после 2 клавиш: ровно 31 строка `[xhci] kbd ev`, потом тишина, ретраи
  идентичны (Send-Bs 2/12, Type-Keys 0/9). Мышь работала — её кольцо за
  прогон не доходило до wrap.
- **Причина:** `TRBS = 32`, link TRB на индексе 31. При wrap старый код
  писал link, потом инвертировал `cycle`, потом вызывал `set_link_cycle`
  с **новым** циклом — но контроллер сверяет toggle-бит link TRB со
  **старым** lap-циклом, когда доходит до конца кольца. Несовпадение ⇒
  кольцо навсегда вставало на первом wrap, то есть на 31-м armed
  EP1-переносе. Тот же порядок с багом сидел в `push_ep0` (EP0 вставал
  после 31 control-переноса) и `cmd_run` (после 31 команды).
- **Фикс/проверка:** link пишется со старым циклом до инверсии (no-op на
  первом лапе, корректно дальше). J теперь сообщает `[kbd ev]` = 70,
  `FAIL` = 0; M (0.5 с), H (37/37), I (8/8) зелёные на том же ISO.

## РЕШЕНО (v2.38.36): флаки потери клавиатурного ввода при входе в GUI / наборе в полях (буфер скан-кодов с одним слотом)
- **Статус:** РЕШЕНО в v2.38.36 — keyboard FIFO (кольцевой буфер на 256
  слотов, `key_push`/`key_pop`), который idle-цикл выгружает до мышиных
  полос, плюс сброс backlog на краю клика и посимвольный ground truth в
  serial.
- **Симптом:** флейки дня смоуков 02.10.2026 (v2.38.35) — прогон 1 вошёл
  в GUI, но набор в поля Network пришёл неверно (`Apply` так и не дал
  `[serial] [net] config applied dhcp=0 ip=10.0.2.15`), прогон 2 вообще
  не вышел из TUI. В день v2.38.36 тот же класс проявился как
  `ssid len 5` после набора `SecureNet` (C) и обрезанный static-конфиг
  (A): QEMU TCG останавливает main-loop гостя на 1–2 с, и пока он стоит,
  каждый новый IRQ затирал единый слот `LAST_SCANCODE` новым
  break-/make-кодом — пачки ввода терялись пропорционально длине stall'а.
- **Первопричина:** у клавиатуры не было очереди: один байт хранился на
  IRQ, а idle-цикл читал его в своём темпе (тот же дизайн с одним слотом,
  что мышиная сторона уже заменила в v2.38.30). Хуже: клик по полю/Connect
  мог обработаться раньше, чем набранные символы успели доехать, и они
  падали не в то поле — serial-логи это доказали (`type 'r' focus=5`,
  затем клик pass-поля, затем `type 'e' focus=6`).
- **Фикс:**
  1. `interrupts::key_push`/`key_pop` — lock-free кольцо на 256 слотов от
     вектора 33 и `ps2::feed_key`; `main.rs` выгружает его `while let
     Some(sc) = key_pop()` до обеих мышиных полос, фильтруя
     extended/shift-коды как раньше.

## РЕШЕНО (v2.38.34): каждая заглавная буква печаталась строчной (состояние Shift терялось в опрошенном пути PS/2)
- **Статус:** РЕШЕНО в v2.38.34 — снапшот shift (`interrupts::SHIFTED`),

- **Симптом:** печать в GUI давала `secu…` вместо `SecureNet` (длина ssid

  `interrupts::SHIFTED` при каждой постановке make-кода в очередь, а

  полным двусторонним слиянием; куча выросла 2 → 4 MiB; стартовый
  self-test фрагментации.
- **Симптом:** долгие сессии на реальном железе в конце концов выдают
  `KERNEL PANIC: memory allocation of N bytes failed` без единого изменения
  кода, которое это объясняло бы — как и сообщал пользователь: «похоже, логи
  переполняются и система падает».
- **Причина:** `FreeListAllocator::dealloc` сливал освобождённый блок только
  с *head* списка свободных. Чередующиеся времена жизни (буфер освобождается,
  пока в голове лежит другой блок — например, мимолётные `format!`-метки при
  рендере GUI) накапливали соседние, но не сросшиеся фрагменты, пока средний
  аллокатор не возвращал null, хотя большая часть 2 MiB кучи была свободна;
  alloc-error путь Rust'а затем паниковал.
- **Фикс:** список свободных хранится в адресном порядке — `dealloc`
  вставляет по порядку и сливается с *обеими* соседями при смежности, `alloc`
  оставляет остаток сплита на его исходном адресе, чтобы порядок выживал при
  сплитах. `HEAP_SIZE` 2 → 4 MiB (GUI backbuffer стоит на `HEAP_START + 4
  MiB` — впритык, но без пересечения страниц). Новый
  `heap::fragmentation_selftest()` на старте: вырезает 24 × 96 KiB блока,
  освобождает их в порядке аллокации — тот самый узор, который раньше
  фрагментировал старый аллокатор, — затем заново добывает 1.5 MiB
  целиком через `try_reserve_exact` (при регрессии — без паники) и пишет
  `[serial] heap: fragmentation self-test ok` (грепается смоуком) или
  `FAILED`.
- **Проверка:** смоук QEMU v2.38.33 — `fragmentation self-test ok` в serial,
  нет `FAILED`, PANIC 0; clippy/fmt/тесты ядра и workspace зелёные.

## РЕШЕНО (v2.38.30): потеря мышиных дельт, если несколько отчётов приходят между двумя опросами ввода
- **Статус:** РЕШЕНО в v2.38.30 — оба входных банда теперь накапливают, а не
  перезаписывают: `ps2::decode_packet` и обработчик xHCI `harvest_mouse`
  делают `fetch_add` в аккумуляторы, а опрос idle-loop сливает их через
  `swap(0)` (`ps2::mouse_dx/mouse_dy`, `xhci::take_mouse_delta`). Атомики
  «последнего отчёта» xHCI не тронуты — их читает вкладка диагностики HID.
- **Симптом:** большие/быстрые движения мыши приземлялись короче или не по
  той оси. Первый прогон смоука v2.38.30 дал `mouse_move -136 -84`, а клик
  в GUI залогировался в (631,400) вместо ожидаемого (504,316) — ровно один
  127-пиксельный кусок меньше по X (−136 → −9) и вся дельта потеряна по Y
  (−84 → 0); следующее движение (200,122) показало тот же узор (200 → 73,
  122 → 0). Малые дельты (≤127 на ось, один пакет) всегда были верны.
- **Причина:** оба банда публиковали *новейший* отчёт в обычные атомики
  (`MOUSE_DX.store`), а idle-loop читал их один раз на изменение
  счётчика. Контроллер PS/2 разбивает движение больше одного пакета на
  последовательные пакеты; если между двумя опросами попадало больше одного,
  вкладка раннего пакета перезаписывалась до того, как её прочитали, —
  молчаливая зависимость от тайминга потеря.
- **Верификация:** на v2.38.30 тот же `mouse_move -136 -84`, за которым
  идёт `(96,-36)`, сажает клик ровно в (600,280) в serial-логе (кумулятивная
  сумма обеих дельт); остальной QEMU-смоук не изменился (PANIC 0, 6 циклов
  resumed).

## РЕШЕНО в v2.38.18: PAGE FAULT при буте на реальном железе (MSI) на шаге xHCI
- **Статус:** РЕШЕНО в v2.38.18 (маппинг всего BAR-апертура + проверка границ)
- **Симптом:** бут MSI падает на шаге xHCI даже со свежим образом:
  `PAGE FAULT: addr=0xffffff00200ed028 ip=0xffffffff8000e81c err=0x2` (запись в
  неприсутствующую супервизорную страницу). Тот же виртуальный адрес фолтил на
  v2.38.16 (ip=0xffffffff8000c75f) — значит это детерминированный баг, а не
  несвежая флешка.
- **Первопричина:** дизассембл release ELF в точке IP краха даёт точную
  падающую инструкцию `movl $0x1, 0x28(%r12,%rax)` — пробную запись
  `mmio32w(candidate + ERSTSZ, 1)` из поиска runtime-регистров. При `%r12` =
  базе MMIO-окна xHCI и `%rax` = репортируемому контроллером сдвигу RTSOFF
  (base+0x18, замаскирован) запись уходит на окно+0xED028. xHCI на MSI
  репортит **RTSOFF = 0xED000**, что далеко за прежним фиксированным
  `map_mmio(bar, 0x8000)`. У QEMU `qemu-xhci` RTSOFF = 0x1000, поэтому размер
  маппинга проверялся только против эмуляции. (Наблюдавшееся на v2.38.16 «IP
  на байт внутрь movzbl» — артефакт линейного дизассембла: старый ELF достигает
  той же записи ERSTSZ через другой относительный IP.)
- **Фикс:** `pci_bar_size()` прозондирует апертуру BAR из PCI-конфига (маска
  «все единицы», для 32/64-бит); `map_mmio` маппит апертур с клампом в
  `[0x8000, 1 МиБ]`; цикл кандидатов runtime-регистров и офсет doorbell
  проверяются на попадание в реальный замапленный диапазон до любой MMIO-
  записи.
- **Верификация:** serial v2.38.18+ печатает `[xhci] dbg bar=... size=...` с
  `map=N/N/N`; перепроверить на MSI (ожидается), смоук QEMU без изменений.

## РЕШЕНО (v2.38.19): курсор USB-мыши мог частично стираться перерисовкой TUI-дашборда
- **Статус:** РЕШЕНО в v2.38.19 — интерактивный TUI композит курсор последним:
  каждая перерисовка панели (`tui::render()`) завершается перерисовкой стрелки
  8x8 поверх, поэтому курсор над панелью, статус-баром или нижней полосой

  Панель и нижняя полоса глифов перерисовывались каждую секунду (заливка всей
  строки `PANEL_BG`/фоном), поэтому курсор, стоящий под ними, исчезал до

## РЕШЕНО (v2.38.23): мерцание GUI на реальной панели + паника ядра от клавиши Windows (extended-сканкод)

- **Статус:** РЕШЕНО в v2.38.23.
- **Симптом (реальное железо, MSI):** оконный GUI v2.38.22 мерцал на панели
  ноутбука, а нажатие «дополнительной» клавиши (прежде всего Windows) жёстко
  валило ядро.
- **Причина / исправление:**
  - Мерцание — `gui::render()` перерисовывал весь framebuffer на ~20 Гц (каждый
    тик кадренции) плюс после каждого репорта мыши. Теперь рендер по damage:
    каждая мутация отмечает dirty-прямоугольник (`Rect`/`DIRTY`,
    `dirty_all`/`dirty_rect`/`dirty_window`), рендерер перерисовывает только
    области, пересекающие damage, а непрерывные пути (курсор, перетаскивание,
    живая телеметрия System/Uptime) отмечают только свои прямоугольники через
    `mark_live_dirty()`. Простой кадр больше не трогает весь framebuffer.
    Вторым источником мерцания поверх GUI был `interrupts::draw_timer_bar()`
    (~100 Гц по тикам) — теперь он пропускается, пока `gui::active()`.
  - Паника на Win-клавише — extended-сканкоды (префиксы 0xE0/0xE1, напр.
    Win = 0x5B) проходили в ASCII-таблицы GUI/TUI и уходили за границы. Теперь
    они гасятся в источнике на обоих путях ввода: `ps2::feed_key` держит
    одноключевой latch `EXT` (extended-байт и его нагрузка отбрасываются), а в
    ветке `LAST_SCANCODE` (IRQ) в `idle_loop` — парный фильтр `last_sc_ext`.
    `ps2::KEY_SCANCODE`/`KEY_SEQ` несут только простые коды set-1.
  - Невидимые краши — на плате MSI нет serial, а вывод в консоль framebuffer
    закрыт гейтом, пока GUI владеет экраном; паника выглядела как застывший
    рабочий стол. `console::panic_report`/`panic_screen` теперь рисуют
    `KERNEL PANIC: …`/`FATAL …` прямо на framebuffer (без блокировок и
    аллокаций, в обход гейта GUI), подключены в `#[panic_handler]` и в
    `interrupts::fatal`/`fatal_with`.
  - Бонус-фикс по пути: `gui::text_line` рисовал текст тела всех окон в
    абсолютной колонке x=8; теперь текст рисуется внутри своего окна в
    `win.x + 8`.
- **Верификация:** QEMU-смоук через монитор (UEFI/OVMF): после входа в GUI
  screendumps с интервалом 1 с байт-в-байт идентичны в статичной области фона
  и в (заглушённом) углу таймер-бара, тогда как пиксели живого окна System
  меняются (перерисовки ограничены dirty-областью); `sendkey meta_l` +
  `meta_r` дали ноль строк `KERNEL PANIC`/`FATAL`, а `[serial] tick`
  продолжил расти (496 с).

## РЕШЕНО (v2.38.25): клиентское окно ring-3 пряталось под встроенными

- **Статус:** РЕШЕНО в v2.38.25 (`raise_clients()` в `gui::enter()`).
- **Симптом:** первый QEMU-прогон нового демо `SYS_GUI` логировал
  `[serial] [gui] ring3 pid 5 registered client window 0 (96x64)`, но на
  screendump видны были только 16 верхних строк тела 96×64 — diff пикселей

- **Причина:** клиентские окна регистрируются, пока экран ещё у консоли (задолго

- **Фикс:** `enter()` теперь поднимает все зарегистрированные клиентские окна на
  вершину z-порядка через `raise_clients()` (в порядке убывания слотов, чтобы
  сдвиги `bring_to_front` не инвалидировали ещё не обработанные индексы) перед
  первым рендером.
- **Проверка:** QEMU-смоук (UEFI/OVMF): тело клиента ровно
  (592,284)–(687,347) = 96×64 = 6144 пикселя одного цвета, который меняется
  между screendump'ами (ротация заливки); два кадра через 1 с различаются только
  внутри боксов клиента и телеметрии (bbox (592,284)–(725,389)); ноль строк
  `KERNEL PANIC`, `[serial] tick` дошёл до 499 с.

## РЕШЕНО (v2.38.24): остаточный tearing / частичные кадры на панели

- **Статус:** РЕШЕНО в v2.38.24 (настоящая двойная буферизация + публикация
  dirty-прямоугольника).
- **Симптом:** при рендере по damage (v2.38.23) панель по-прежнему писалась
  напрямую в VRAM несколькими проходами за кадр, поэтому обновление панели,
  засканнировавшее строй посреди рендера, могло поймать наполовину
  нарисованные строки (тиринг), а фиксированные ~20 Гц делали живую телеметрию
  видимо ступенчатой.
- **Причина / фикс:** рендер теперь двухэтапный. Вся отрисовка идёт в
  RAM-бэкбуфер (`Framebuffer::from_ram`, плотная поверхность того же формата),
  где лежит полный рабочий стол; только после полной отрисовки кадра
  прямоугольник повреждений публикуется в VRAM через `Framebuffer::blit_region`
  — ровно одна `copy_nonoverlapping` на строку. Панель, следовательно, сканирует
  только полный предыдущий или полный новый кадр: ни фликера, ни рваных строк.
  `idle_loop` гоняет GUI на собственном гейте «каждый тик» (≈100 FPS) вместо
  общего гейта 20 Гц.
- **Известный компромисс:** бэкбуфер держит память размером с экран всё время
  аптайма (4 МиБ на 1280×800; ~8 МиБ на 1920×1080; берётся из frame-аллокатора,
  никогда не освобождается — в том же стиле, что bump-аллокатор). На системах с
  малой памятью маппинг может не удаться: тогда `ensure_backbuffer` ставит
  `BACKBUF_FAIL`, и GUI деградирует на прямой VRAM-рендер v2.38.23 с той же
  damage-логикой (`[serial] gui backbuffer …` логируется только при успехе).
- **Проверка:** QEMU-смоук (UEFI/OVMF) логирует
  `[serial] gui backbuffer 4000 KiB at 0xffffff0000400000`; два screendump'а с
  интервалом 1 с различаются только в 832 из 1 024 000 пикселей, все внутри
  бокса телеметрии (606,326)–(727,389) — 99,92% байт-в-байт идентичны, т.е. ни
  полной перерисовки, ни частичных строк; `sendkey meta_l/meta_l/meta_r` не дал
  ни одной строки паники, `[serial] tick` дошёл до 470 с.

## РЕШЕНО (v2.38.20): разыменование RSDP давало #GP(0) — RSDP от Limine уже со смещением HHDM
- **Статус:** РЕШЕНО в v2.38.20
- **Симптом:** на QEMU ядро падало сразу после первого LAPIC-тика с
  `GENERAL PROTECTION FAULT rip=… err=0x0` до любых строк `[acpi]`, а после
  первого фикса обход XSDT фолтил страницей (`PAGE FAULT: addr=0x1f77d0ec` —
  физический адрес слота длины XSDT).
- **Первопричина:** Limine отдаёт указатель RSDP уже с HHDM-смещением
  (`rsdp = 0xffff80001f77e014`), поэтому прежний `physical_to_virtual(rsdp)`
  прикладывал смещение дважды → не-канонический `0xffff0000_1f77e014` → #GP(0).
  Последующее чтение длины XSDT фолтило, потому что `find_entry`
  разыменовывал *физический* адрес корня без HHDM-смещения вообще.
- **Фикс:** `acpi.rs::virt_addr()` принимает любую форму (голый physical или
  уже со смещением), а `find_entry` маппит корневую таблицу через
  `memory::physical_to_virtual` перед чтением заголовка/слотов записей; поля
  FADT и так шли через маппинг. Бут теперь на QEMU логирует `[acpi] rev=2
  XSDT@…` и `fadt rev=1`.
- **Верификация:** смоук QEMU (v2.38.20) доходит до idle-цикла со всеми
  четырьмя платформенными модулями; перепроверить на MSI.

  область GOP (у < text_height) с вертикальным повторением периода 16 пикселей:

  поэтому однократный оверлей (например, стрелка курсора 8x8) на скриншотах

- **Доказательство, что это квирк пути рендера, а не дефект ядра:** смоук мыши
  (v2.38.16) подтвердил оба конца независимо — serial показывает

  фреймбуфера ядра по нарисованному тайлу 8x8 воспроизводит битовую карту
  стрелки 1:1. TUI-дашборд (перерисовывается каждую секунду) в тех же
  скриншотах рендерится живо — повторяется только консольная область.
- **Обход/фикс:** принимать serial + readback как доказательство в QEMU, а
  визуально проверять курсор на реальном железе (MSI); при наличии окна можно
  дополнительно перепроверить реальным дисплейным бэкендом (например,
  `-display gtk`).

## РЕШЕНО: «Чёрный экран» при старте графики ядра/TUI (расследование, дефект не найден)
- **Статус:** РЕШЕНО в v2.38.13 (ужесточение + загрузочная верификация)
- **Симптом (гипотеза):** пустой/чёрный GOP framebuffer под TUI и консолью.
  **Не воспроизводится** — рендер подтверждён в QEMU-смоуках и на MSI
  (дашборд v2.38.11), поэтому задание отработано как профилактический
  hardening.
- **Находки (защита от фейк-фикса):** Limine передаёт ядру framebuffer, чей
  `address` **уже содержит off-сет HHDM** — протокол гласит: «все не-null
  указатели указывают на объект с уже добавленным off-сетом Higher Half
  Direct Map», и сам загрузчик задаёт `fb.address = fb_phys + direct_map_offset`.
  AIOS пишет через этот указатель как есть (`Framebuffer::new` →
  `base_addr()`), поэтому повторное добавление `physical_memory_offset`
  сдвинуло бы указатель дважды и вызвало фолт. Limine мапит HHDM (включая
  область framebuffer) как `-rwx`; `NO_EXECUTE` на страницах VRAM не
  выставляется by design — «требование PRESENT|WRITABLE|NX» из другой
  кодовой базы здесь неприменимо.
- **Сделано в v2.38.13:** `memory::verify_region()` проходит по живым
  таблицам страниц на весь диапазон `pitch * height` VRAM, в лог загрузки
  добавлены `framebuffer address` и `framebuffer pages: N present, M writable,
  K total`; прямой цветотест стал `framebuffer::direct_test()` — запись строго
  через `core::ptr::write_volatile` с адресацией пикселей по физическому
  stride (`pitch / bytes_per_pixel`), плюс `sfence` и readback пикселя (0, 0);
  `psf.rs` добавляет `no_std`-парсинг PSF1/PSF2 и загрузочную проверку
  round-trip.
- **Защита от регрессий:** при загрузке должны быть `framebuffer pages:
  <present==total> present, <writable==total> writable`, `direct colour test OK
  (readback …)` и `[psf] PSF2 w=8 h=8 glyphs=128 'A'=match`.

## РЕШЕНО: `#GP err=0x28` на `iretq` при первом аппаратном тике — CS/SS от Limine не перезагружались
- **Статус:** РЕШЕНО в v2.38.12
- **Симптом (QEMU после `sti` и реальное железо):** первый тик таймера
  (вектор `0x90`, LAPIC; ранее вектор `32`, PIT) входил в обработчик
  нормально, `fatal()` печатал `GENERAL PROTECTION FAULT`, и фолт был на
  `iretq` в irq-стабе. Фрейм выглядел корректным: `vector=0x90 error=0`
  `rip` внутри boot-пробы (под защитой `sti`), `cs=0x28`, `ss=0x30`,
  `rflags=0x10246`. В фрейме сохранялись селекторы Limine, а не AIOS.
- **Корневая причина:** Limine передаёт загрузочному CPU `CS=0x28/SS=0x30`
  (селекторы своей GDT — валидные code/data дескрипторы). AIOS ставит свою
  GDT (`lgdt`), но — до этого фикса — никогда не перезагружал CS/SS, поэтому
  CPU продолжал работать на *закешированных* дескрипторах Limine (в long
  mode это легально). Первое прерывание затем клало в interrupt-фрейм
  сохранённые значения `cs=0x28/ss=0x30`, а `iretq` перевалидировал
  `CS=0x28` по GDT AIOS, где на слотах 5/6 лежит **дескриптор TSS** → `#GP
  err=0x28`. Загрузка шла только потому, что long mode не перечитывает
  сегментные дескрипторы, пока их не заставит load/far-return/`iretq`.
- **Фикс:** `aios_reload_segments` (`gdt.rs`) после `lgdt` теперь
  перезагружает `ss=0x10` и делает far return в `CS=0x08` через собственную
  GDT AIOS. Interrupt-фреймы после этого сохраняют `cs=0x8/ss=0x10`, и
  `iretq` валидирует их корректно. Проверено в QEMU: `[lapic] tick cs=0x8
  ss=0x10` при первом срабатывании, затем тысячи тиков без фолта.
- **Объяснено заодно:** GP#13 v2.38.0 «порча IDT-шины PIT» на реальном
  железе и GP в этом сеансе — тот же дефект; теории «повреждённый байт» и
  «фрейм 24 vs 40 байт» были симптомами. Невидимый PIT-бар v2.38.5 на MSI
  тоже объяснён: первый PIT-тик давал #GP внутри `iretq` до того, как
  `draw_timer_bar` мог отработать.
- **Защита от регрессий:** в загрузке должны быть `boot selectors cs=0x28
  ss=0x30 ds=0x30` и затем `[lapic] tick cs=0x8 ss=0x10`; аппаратные тики
  должны копиться без fatal.

## ИСПРАВЛЕНО: демо-IPC ping-pong молча маршрутизировался не туда (строки `[ipc]` не печатались)
- **Статус:** ИСПРАВЛЕНО в v2.38.11
- **Симптом (QEMU и MSI, v2.38.9-10):** демо send/receive работает (каждый
  раунд `u1`/`u2`/`*`, все циклы sleep/wake), но proof-строки `[ipc]
  send/recv` не появляются никогда, сколько бы ни работала ОС; строка IPC
  дашборда v2.38.11 замирала на sent=0/recv=0.
- **Причина:** адресат `SYS_SEND`, зашитый в демо-машину, был константой
  `PID_*` (1/2), а в рантайме `current_pid()` возвращает **слот планировщика**
  задачи (2/3/4 — слот 1 принадлежит kernel worker'у). `user::init()`
  спавнил программы в порядке **A, C, B**, поэтому A заняла слот 2, а B —
  слот 4: посылка A попадала в её же слот (`src == dst`), отбрасывается
  `send()` молча; посылка B — в ящик kernel worker'а, который никто не
  опустошает. При глубине ящика 16 ping-pong не завершал ни одной доставки —
  счётчик, дающий сэмплы `val % 8`, не сдвигался.
- **Фикс:** `user::init()` теперь спавнит строго A → B → C (слоты 2/3/4), а
  демо-машины шлют на явные константы слотов-собеседников `SLOT_A = 2` /
  `SLOT_B = 3` вместо `PID_*`. Doc-комментарий `init()` предупреждает, что
  изменение порядка спавна молча ломает IPC.
- **Регрессионная защита:** smoke-прогон обязан показывать `[ipc] send …` +
  `[ipc] recv …` при `val=8` (QEMU ~10 с); строка IPC дашборда — растущие
  итоги sent/recv.

## ИСПРАВЛЕНО: демо ring-3 pid3 парковалось в busy-spin и замораживало ОС на платах без PIC
- **Статус:** ИСПРАВЛЕНО в v2.38.10
- **Симптом (MSI, v2.38.9):** через ~8 раундов демо лог останавливается на
  `[ktask] alive #8` … `[sched] pid3 woke`; квадрат heartbeat 2 Гц замирает;
  по экрану вверх растянуты зелёные копии квадрата самопроверки.
- **Причина (два бага):**
  1. `build_pid3` заканчивался `jmp $` (бесконечный спин). На платах без
     8259 PIC планировщик не может вытеснить работающую задачу, поэтому
     крутящаяся ring-3 задача никогда не отдаёт CPU → `idle_loop` (источник
     software-tick и heartbeat) не запускается → `TICKS` встаёт, спящие
     pid1/pid2 не просыпаются, ядро выглядит зависшим. В QEMU аппаратный PIT
     вытесняет — поэтому баг не ловился: **вытесняющего планирования на PIT-
     less железе нет** — планировщик там кооперативный.
  2. `scroll_up` memmove'ил весь кадр, таская копии нижнего heartbeat-overlay
     (и PIT-бара сверху) вверх с каждым скроллом консоли — «движущиеся
     зелёные квадраты».
- **Фикс:** pid3 теперь зациклен на свой sleep-цикл вместо парковки
  (`jmp_self` удалён) и продолжает отдавать CPU — экономика тиков живёт
  вечно. Консоль резервирует нижнюю строку `GLYPH_H` под heartbeat-overlay,
  а `scroll_up` ограничен областью консоли — overlay не скроллится/не
  дублируется.
- **Регрессионная защита:** ни одна демо-задача не должна заканчиваться
  busy-циклом; каждая ring-3 программа обязана отдавать CPU (`SYS_SLEEP`)
  с какой-то периодичностью.

## РЕШЕНО: IRQ0 от PIT не приходит на ноутбуке MSI — 8259 PIC мёртв в UEFI APIC-режиме
- **Статус:** РЕШЕНО в v2.38.12 таймером Local APIC (был ПОДТВЕРЖДЁН в
  v2.38.6-7, смягчено software-tick фолбэком)
- **Симптом:** загрузка полностью проходит (14/14 шагов; три ring-3 задачи
  работают, `getpid`/`write` отвечают, каждая спит 20 тиков), затем вывод
  обрывается на `[sched] idle`. `[tick]`, `[sched] pid N woke` и heartbeat
  2 Гц не появляются, PIT-бар v2.38.5 справа сверху остаётся высотой 0
  (невидим) на MSI.
- **Подтверждение:** с software-tick фолбэком v2.38.6 загрузка на MSI больше
  не зависает — `[ktask] alive` растёт, все три ring-3 задачи просыпаются,
  работают и снова засыпают в цикле, доказывая, что планировщик был здоров,
  а не хватало только аппаратного таймерного IRQ. `[sched] idle` ограничен
  1/с в v2.38.7 (фолбэк печатал ~100 idle-строк/с).
- **Корневая причина:** legacy 8259 PIC не доставляет IRQ0 до CPU на этом
  UEFI-ноутбуке (линия идёт через незапрограммированный IO-APIC), поэтому
  `TICKS` не меняется никогда. Все последующие симптомы — каскад от
  замороженного счётчика тиков.
- **Решение (v2.38.12):** таймер Local APIC (`lapic.rs`) теперь даёт реальные
  аппаратные тики 100 Гц на векторе `0x90`, полностью независимо от 8259
  PIC — программировать IO-APIC не нужно, Local APIC есть в каждом
  x86/x86-64 процессоре. Счётчик PIT остаётся источником калибровки и
  software-tick фолбэком, который по-прежнему охраняет `IRQ32_SEEN`.
- **Доказательный путь в v2.38.6:** при загрузке печатается на экран
  `[probe] irq32_seen=.. ticks=..->.. (delta N)` после ~120 мс отсчёта по
  PIT; `delta 0` + `irq32_seen false` подтверждают мёртвый PIC.
- **Смягчение (остаётся как фолбэк):** software-tick фолбэк в `idle_loop` —
  если тик-прерывание ещё не приходило, idle опрашивает всегда работающий
  счётчик PIT в течение одного тикового периода (~10 мс) и сам увеличивает
  `TICKS`, оживляя sleep, `[tick]` и heartbeat на любой плате.
- **Защита от регрессий:** `IRQ32_SEEN` отличает рабочую PIC (`hlt`-путь,
  аппаратные тики) от мёртвой (poll-путь); двойного счёта нет. `tui.rs`
  показывает `HW-LAPIC`/`HW-IRQ`/`SOFT`, чтобы активный источник тиков был
  виден на дашборде.

## ИСПРАВЛЕНО: v2.38.0 коррупция IDT-шины PIT вызывает GP#13 на реальном оборудовании
- **Статус:** ИСПРАВЛЕНО в v2.38.1 (маскирование IRQ 0)
- **Симптом:** на реальном ноутбуке с загрузочной AIOS-флешкой ядро
  достигает `scheduler online` и тут же останавливается. На
  serial-консоли видно `[serial] scheduler online, IPC + user syscalls armed.`
  и ничего больше. Система зависла.
- **Причина:** IDT-шина для вектора 32 (PIT) имеет повреждённое поле
  `offset_mid`. После `sti` таймер срабатывает немедленно, CPU
  ищет повреждённую запись IDT, возникает GP#13
  (General Protection Fault). `fatal()` останавливает систему.
- **Исправление:** маскирование IRQ 0 в OCW1 PIC (`0xFC` → `0xFD`)
  в `init_pic()`. Ядро загружается до `scheduler online` без
  сбоя. Кооперативное планирование через `yield_kernel()`
  (`int 0xfa`) работает корректно. Ввод с клавиатуры
   остаётся недоступным из-за ограничения xHCI (BUG-044).
**Вторичная проблема:** `serial::write_bytes` ожидает бит THRE
   (байт 5 регистра COM1+5) в бесконечном цикле `while`. На реальном
   оборудовании без подключённого последовательного порта THRE может
   никогда не стать установленным, что вызывает бесконечное зависание
   на `kprintln!` после `scheduler online` (`main.rs:521`). Исправлено
   добавлением таймаута 0xFFFF: если THRE не установился за это время,
   запись пропускается и ядро продолжает работу.

## ДИАГНОСТИКА: v2.38.2 Режим отладки F8 + HALT_REASON и логирование шагов загрузки
- **Назначение:** определить точно, где ядро останавливается на реальном оборудовании.
- **Режим F8:** нажмите **F8** сразу после появления экрана BIOS/UEFI и до начала вывода ядром. Контроллер клавиатуры i8042 опрашивается на нажатие F8 (make-код `0x38`). Если обнаружена, `DEBUG_MODE: AtomicBool` устанавливается и в **верхнем-left углу** framebuffer выводится debug-баннер со всеми 14 маркерами `STEP`. Без F8 ядро загружается тихо (только TUI, без маркеров).
- **Механизм:** при активном режиме отладки `print_step()` печатает `STEP X/14: message` в области верхнего-left угла. При критической ошибке `HALT_REASON: AtomicU32` сохраняет код (0x80000000+), debug port `0x80` получает младший байт, и `vprintln!` + `kprintln!` выводят код и описание перед остановкой.
- **Использование:** на реальном ноутбуке, если система останавливается на `STEP 7/14`, последний напечатанный шаг определяет область сбоя. Значение debug port `0x80` можно прочитать аппаратным пробником или внешним анализатором логики.
- **Коды ошибок:** `0x10000000 + vector` для прерываний, `0x20000000` для page fault, `0x30000001` для неудачи self-теста пейджинга.
- **Файлы:** `aios-kernel/src/interrupts.rs`, `aios-kernel/src/console.rs`, `aios-kernel/src/main.rs`.

## ИСПРАВЛЕНО: `memset` из `crt.rs` (v2.35.0) вешал загрузку (циклический PLT)
- **Статус:** ИСПРАВЛЕНО в v2.36.0 (модуль удалён)
- **Симптом:** ядро зависало на середине загрузки сразу после `[serial] heap online.` — строка `interrupts online.` не появлялась, исключение не печаталось.

## ИСПРАВЛЕНО: HHDM Limine не покрывает MMIO (обращение к BAR даёт page fault)
- **Статус:** ИСПРАВЛЕНО в v2.36.0
- **Симптом:** чтение ABAR AHCI через HHDM-алиас давало `PAGE FAULT: addr=0xffff800081060004 ip=0xffffffff80007420 err=0x0`; ранее то же обращение приводило к triple fault, так как выполнялось до `sti`.
- **Причина:** HHDM Limine маппит только пригодную RAM, но не области MMIO устройств, поэтому `hhdm_offset + phys` для BAR не отображён.
- **Исправление:** добавлен `memory::map_mmio(phys, size)` (маппит выровненные по страницам страницы устройств в выделенное окно `0xffffff00_2000_0000`, слот PML4 510), а инициализация драйверов перенесена **после** `sti`, чтобы исключения обрабатывались ядром.

## ИСПРАВЛЕНО: подъём NVMe в v2.37.0 — `CSTS.CFS` при запуске и таймауты admin-команд
- **Статус:** ИСПРАВЛЕНО в v2.37.0 (драйвер добавлен)
- **Симптом:** драйвер NVMe сразу после записи `CC.EN=1` выставлял `CSTS.CFS` (`nvme: controller fatal status`), а после исправления этого первая admin-команда уходила в таймаут.
- **Причина:** (1) в `AQA` поле `ASQS` — биты 11:0, а `ACQS` — биты **27:16**: изначальный сдвиг `<< 12` оставлял `ACQS = 0`, и QEMU отклонял запуск (`pci_nvme_err_startfail_acqent_sz_zero`); (2) фазовый бит записи завершения — это бит 0 16-битного поля статуса (бит 16 двойного слова), а не бит 31, поэтому опрос никогда не замечал завершение.
- **Исправление:** `AQA = (depth-1) | ((depth-1) << 16)`, а проверка фазы использует `(status >> 16) & 1` (поле статуса читается как `(status >> 17) & 0x7FFF`). Диагностировалось через QEMU `-trace enable=pci_nvme_*`.

## ИСПРАВЛЕНО (v2.38.1): xHCI опрашивает только первое USB-устройство при загрузке с флешки (BUG-044)
- **Статус:** ИСПРАВЛЕНО в v2.38.1 (перечисление всех root-портов)
- **Симптом:** `xhci.rs` вызывал `reset_port()` который возвращал первый порт с `PORT_CCS`. Когда флешка занимала этот порт, `find_hid_ep` падал с `xhci init failed: xhci: no HID interrupt IN endpoint in configuration` и ядро доходило до `scheduler online` **без вооружённой клавиатуры**.
- **Причина:** `reset_port()` перебирал порты и возвращал первый с `PORT_CCS`, не проверяя класс устройства.
- **Исправление:** `reset_port()` заменён на `find_hid_port()` который перебирает **все** root-порты, сбрасывает каждый, вызывает `enable_slot`/`address_device`/`get_descriptor`/`find_hid_ep` для каждого, и возвращает первый порт с HID-клавиатурой. На QEMU это корректно пропускает порты 1-4 (mass storage) и выбирает порт 5 (usb-kbd устройство).
- **Верификация:** QEMU UEFI показывает `port 1-4 portsc=0x000202a0` (пропущены) и `port 5 portsc=0x00020ee1` → `usb hid boot keyboard armed.` → `scheduler online, IPC + user syscalls armed.`

## ИСПРАВЛЕНО: носитель Live/Installer давал чёрный экран после меню загрузки на реальном ноутбуке
- **Статус:** ИСПРАВЛЕНО в v2.33.3 (сообщено пользователем: «при выборе Live или Installer загружается vmlinuz, потом initramfs — и на этом всё стоит, чёрный экран»)
- **Симптом:** меню загрузчика Limine на экране ноутбука показывалось; при выборе любой записи грузились `vmlinuz` + `initramfs`; затем экран чернел и оставался чёрным — а сама система при этом продолжала (невидимо) грузиться. Тот же носитель проходил наши QEMU-тесты, потому что харнесс снимает именно serial-консоль.
- **Причина (анализ v2.33.2, неполный):** фикс v2.33.2 (серийная консоль → `tty0`) проверялся через видеодамп QEMU, но на ноутбуке экран оставался чёрным. Настоящая причина: в initramfs **нет драйвера VGA-консоли** (`vgacon`/`vesafb`/`efifb` отсутствуют, `simpledrm` встроен, но не даёт фреймбуфера, пока fbcon не зарегистрирует), поэтому консоль `tty0` нечему было рисовать, — а GPU-DRM-модули **не грузились до юзерспейса** (а поставленный `aios-init` вообще не вызывал `bring_userspace()`/`sfs-up.sh` для подъёма GPU). Одного `console=tty0` было недостаточно.
- **Исправление (v2.33.3):** запись `/init` в initramfs теперь — это пре-инит скрипт `aios-loader` (выполняется до юзерспейса), который `modprobe`'ит все пять x86 GPU-DRM-драйверов (`radeon`, `nouveau`, `gma500_gfx`, `i915`, `amdgpu`) — давая fbcon фреймбуфер заблаговременно, — затем `dd`-извлекает встроенный оригинальный ELF `aios-init` (с запечёнными фиксированной ширины `BINOFF`/`BINSZ`) и делает `exec`, сохраняя цепочку PID 1. Обе записи Limine также получили `loglevel=7`, чтобы отложенный лог ядра был виден сразу после регистрации fbcon. Ограничение ядра распаковки initramfs: работает **только** in-place замена содержимого записи `/init` — добавленные после её игнорируются, а удаление/переименование `/init` заставляет ядро отвергнуть весь архив.
- **Обходной путь / примечания:** после фикса не нужен. Связанное известное ограничение: гибридный ISO — legacy-MBR (BIOS-часть Limine) — чистый UEFI без CSM и Secure Boot его не загрузят; отслеживается в `docs/TODO.md` (приёмка на реальном железе).

## ИСПРАВЛЕНО: фантомный `USB 0000:0000 (unknown)` провижинится по кругу — «при каждом открытии вкладки 1 появляется новая строка»

- **Симптом:** на вкладке System & HW лента тостов `Events` и правая панель журнала постоянно пополнялись: `HAL: NVIDIA GPU detected …` / `HAL: Detected 16 cores…` каждые несколько секунд и повторяющийся тост провижининга `[Hardware] USB 0000:0000 (unknown) -> driver not found… -> Generic Fallback`. ## ИСПРАВЛЕНО: ядерный TUI рисовал шкалу RAM поверх полосы статуса на низком окне («всё в кучу» при переключении вкладок)
- **Статус:** ИСПРАВЛЕНО в v2.31.1 (сообщено пользователем: «при использовании переключая между вкладками распадается интерфейс и потом все в кучу становится»)
- **Симптом:** на малых высотах терминала вкладка System & HW (1) выглядела как нагромождение виджетов — строка ` RAM Usage ` лежала на строке полосы статуса (`AIOS v…` не виден), блоки CPU/OS схлопывались, Hardware Inspector и журнал расползались. Воспроизведено детерминированно на 50×14 и разобрано с помощью render-харнесса на `TestBackend` + дампов строк.
- **Причина:** `draw_system_tab` позиционировал шкалу RAM как `Rect::new(x+2, chunk.y + chunk.height - 3, w-4, 3)`. ratatui считает констрейнты `Length` жёсткими равенствами и сжимает их пропорционально, когда сумма (9+8+10=27) превышает высоту панели; при высоте панели ≤ 9 чанк CPU получает `height == 0`, и `y` шкалы становится `chunk.y + 0 - 3`, что при `chunk.y == 3` даёт строку `0` — зону полосы статуса. `Flex::Start` не помогает: flex влияет только на спейсеры.
- **Исправление:** прямоугольник шкалы ограничен через `saturating_sub` и по высоте, и по ширине; шкала рисуется только при `width > 10 && height > 0`, поэтому больше не может покинуть левую панель. Прочие источники наложений закрыты смоук-тестом рендера, прогоняющим все размеры.

## ИСПРАВЛЕНО: куча aios-kernel возвращала повреждённые данные после роста `Vec` (устаревший размер блока при выделении)

## ИСПРАВЛЕНО: aios-kernel, веха 1 — тройной фолт при инициализации GDT/IDT (раскладка packed-дескриптора)
- **Статус:** ИСПРАВЛЕНО в v2.27.0 (найдено при подъёме прерываний вехи 1 под QEMU)
- **Симптом:** ядро загружалось до вехи 0, затем умирало внутри `gdt::init` без сообщения о панике. QEMU `-d int` показывал одиночный `v=0d` (#GP) на `aios_reload_segments` / `ltr`, затем `v=08` (double fault) и тройной фолт; дамп регистров при фолте показывал `GDT= d960000000000000 0000003f` и `IDT= d9f0000000000000 00000fff` — базы GDTR/IDTR были обрезаны (младшие 16 бит реальной базы).
- **Причина:** `struct Descriptor { limit: u16, base: u64 }` был `#[repr(C)]`; выравнивание `u64` сдвинуло `base` на смещение 8 и оставило 6 байт padding на 2..8. CPU читает операнд `lgdt`/`lidt` как непрерывный 10-байтовый дескриптор — limit на смещении 0, base на смещении 2. Поэтому загружаемая база получалась как `padding + первые два байта базы` (например, `0xd960` вместо `0x1000001d960`), и GDT/IDT указывали в мусор. Любая загрузка дескриптора через новую GDT фолтила: `retfq`/`mov ds, 0x10` → `#GP`, доставка исключения через сломанную IDT → `#DF` → тройной фолт.
- **Исправление:** оба дескриптора помечены `#[repr(C, packed)]` (base теперь начинается со смещения 2, как читает CPU), а поле `descriptor` доступно через `addr_of_mut!` (поля packed-структур не выровнены). `gdt.rs` и `idt.rs`.
- **Обходной путь / примечания:** не требуется после фикса; подтверждено запуском вехи 1 под QEMU (`[serial] Milestone 1: interrupts online.`, `tick 1s/2s/...`, `key 'h' (0x23)` через монитор QEMU).

## ИСПРАВЛЕНО: код `aios_reload_segments` попал в секцию данных (утечка `.section` между `global_asm!`)
- **Статус:** ИСПРАВЛЕНО в v2.27.0 (найдено при подъёме прерываний вехи 1)
- **Симптом:** `aios_reload_segments` залинковался в `.data.rel.ro` (секция данных) вместо `.text`; `nm` сообщал `D aios_reload_segments` в диапазоне `.data.rel.ro`.
- **Причина:** Rust склеивает все блоки `global_asm!` в один ассемблерный поток. Сгенерированный `irq_stubs.S` излучает `.section .data.rel.ro` для `aios_handler_table`, и ассемблер сохраняет эту секцию текущей; следующий `global_asm!` (модуль `gdt`) без явной секции попадает в `.data.rel.ro`.
- **Исправление:** явный `.text` в начале `global_asm!` модуля `gdt`. Также убран ненужный дальний возврат для перезагрузки CS (`retfq`); загрузчик уже запускает ядро с CS=`0x08`/SS=`0x10`, которые после `lgdt` резолвятся в собственные дескрипторы ядра, поэтому `reload_segments` перезагружает только DS/ES/FS/GS.
- **Обходной путь / примечания:** не требуется после фикса.

## ИСПРАВЛЕНО: aios-kernel, веха 0 — тройной фолт при первой загрузке (запись в непроецированный VGA по 0xB8000)
- **Статус:** ИСПРАВЛЕНО в v2.26.0 (найдено при проверке первой загрузки под QEMU)
- **Симптом:** QEMU загружал загрузчик, точка входа ядра достигалась, затем CPU делал тройной фолт. Serial-лог заканчивался на `Jumping to kernel entry point at VirtAddr(0x100000028a0)`; QEMU `-d int` показывал `old: 0xe new 0xe`, затем `v=08` (double fault), с `RAX=0xB8000`, `IP=0x10000001a40` (`movw $0x720,(%rax)`) и `CR2=0xE0`.
- **Причина:** дефолтный `Mappings` загрузчика задаёт `physical_memory: Option::None` — проецируются только сегменты ядра, boot info, стек и кадровый буфер, а нижняя физическая память — нет. Цикл очистки VGA писал в текстовый буфер по физическому адресу `0xB8000`, у которого нет маппинга → page fault. Так как ядро ещё не установило IDT, выборка дескриптора IDT по базе 0 (вектор 0xE → линейный адрес `0xE0`, отсюда `CR2=0xE0`) сама давала фолт → double fault → triple fault.
- **Исправление:** `aios-kernel` теперь создаёт `BootloaderConfig` с `config.mappings.physical_memory = Some(Mapping::Dynamic)` и передаёт его в `entry_point!(kernel_main, config = &BOOTLOADER_CONFIG)`. `kernel_main` передаёт `physical_memory_offset` в `vga::vga_init`, который перенаправляет `VgaWriter::buffer_addr` на `0xB8000 + offset`, так что буфер VGA доступен через карту физической памяти.
- **Обходной путь / примечания:** не требуется после фикса; подтверждено смоук-запуском вехи 0 под QEMU (`[serial] Milestone 0 OK.`).

### ИСПРАВЛЕНО: VRAM показывался как 4.0 GB для видеокарт больше 4 ГиБ в ядерном TUI
- **Статус:** ИСПРАВЛЕНО в v2.25.2 (найдено при живом запуске)
- **Симптом:** `aios` (ядерный TUI) верно определял модель видеокарты, но всегда показывал 4.0 GB VRAM (RTX 3060 на 12 ГБ отображалась как «4.0 GB VRAM»), тогда как GUI/HAL корректно показывал 12288 MB.
- **Причина:** `hw_probe::probe_gpu` читал VRAM из WMI-поля `win32_VideoController.AdapterRAM` (32-битного). Драйверы NVIDIA возвращают «завёрнутое»/усечённое значение для карт больше 4 ГиБ — RTX 3060 отдаёт 4293918720 (0xFFF00000), т.е. 4.0 ГиБ минус 1 МиБ. Существующая проверка на `0xFFFFFFFF` покрывала только «неизвестное» значение, а не заворот.
- **Исправление:** `probe_gpu` теперь сначала использует `aios_hal::hardware::HardwareProfile::detect()`, который читает реальный VRAM через `nvidia-smi --query-gpu=memory.total` (в МиБ). Путь через WMI остался только как запасной источник имени; добавлены конвертер `gpu_from_hal` и регрессионные тесты.
- **Обходной путь / примечания:** не требуется после фикса; покрыто регрессионными тестами в `aios/src/hw_probe.rs`.

### ИСПРАВЛЕНО: `Cannot start a runtime from within a runtime` при старте TUI
- **Статус:** ИСПРАВЛЕНО в v2.25.1 (найдено при живом запуске)
- **Симптом:** `aios` (ядерный TUI) паниковал на `thread 'main'` сразу после HAL-детекции (`HAL: NVIDIA GPU detected … Detected 16 cores, …`) с `Cannot start a runtime from within a runtime` из `tokio-1.53.1/src/runtime/scheduler/multi_thread/mod.rs:91`.
- **Причина:** `main` помечен `#[tokio::main]`, поэтому главный поток уже находится внутри tokio-runtime. Стартовый проход обеспечения (`AutohalEngine::rescan` → `provision_blocking`) и другие синхронные обёртки (`DriverFetcher::sync_get`/`find_driver_sync`, `StoreManager::block_on`) каждый раз строили *свежий* tokio-runtime и вызывали `block_on` изнутри работающего runtime, что tokio запрещает.
- **Исправление:** новый хелпер `aios_core::runtime::block_on_future` — вне runtime строит свежий runtime; внутри multi-thread runtime паркует воркер через `block_in_place` и блокируется на существующем handle (включая не-`Send` футуры); все синхронные обёртки идут через него.
- **Обходной путь / примечания:** не требуется после фикса; покрыто регрессионным тестом `provision_blocking_is_safe_inside_tokio_runtime`.

### ИСПРАВЛЕНО: `Kernel panic: No working init found` при загрузке из initramfs
- **Статус:** ИСПРАВЛЕНО в v2.12.0 (на уровне архитектуры)
- **Симптом:** Когда в initramfs не оказывалось рабочего `/sbin/init` (или скрипт busybox init отсутствовал / не был исполняемым), ядро останавливалось с `Kernel panic: No working init found. Try passing init= option to kernel.`
- **Причина:** Прежний `/init` в initramfs был скриптом на shell (`live/init.rs`) и зависел от наличия исполняемого busybox; любая ошибка упаковки оставляла ядру нечего запускать.
- **Исправление:** Новый крейт `aios-init` — статически слинкованный (`x86_64-unknown-linux-musl`) Rust `/init` (см. `docs/ARCHITECTURE.md`, слой 8). Он никогда не паникует: если `/system/aios-core` или `/installer` отсутствует — переходит в спасательный шелл (`/bin/sh` → `/bin/busybox sh` → `/bin/ash`), а если шелла нет — остаётся в idle-цикле со сборкой `waitpid` вместо завершения (именно выход из PID 1 и провоцирует панику ядра).
- **Обходной путь / примечания:** передавать `init=/init console=tty0` в командной строке ядра (GRUB/Syslinux), чтобы бинарник использовался явно; собирать через `./build_initramfs.sh` (опционально `BUSYBOX_PATH=...` для спасательного шелла). Начиная с v2.13.0 скрипт также собирает и размещает реальный ядерный бинарник `aios` как `/system/aios-core`, поэтому загрузка попадает сразу в полный ядерный TUI; спасательный шелл остаётся только запасным вариантом.

### ИЗВЕСТНОЕ ОГРАНИЧЕНИЕ: статическая сборка `aios` для musl требует native-TLS библиотек на сборочном хосте
- **Статус:** ПО ЗАМЫСЛУ
- **Симптом:** `build_initramfs.sh` (и `live/build.sh` в режиме aios-init по умолчанию) собирают `aios` для `x86_64-unknown-linux-musl`; `reqwest` 0.12 без явной фичи `rustls` линкует native-tls/OpenSSL, поэтому кросс-сборка для musl требует системных dev/static библиотек OpenSSL (в Alpine-контейнере Live ставится `openssl-dev`).
- **Обходной путь:** собирать на хосте, где OpenSSL доступен для musl (Alpine или эквивалентный контейнер); либо использовать `./build_initramfs.sh --no-aios-core` / `SKIP_AIOS_CORE=1`, чтобы получить initramfs только со спасательным шеллом.
- **Примечание:** если сборка aios завершилась ошибкой или была пропущена, скрипт предупреждает и продолжает — загрузка всё равно работает через спасательный шелл.


### ИЗВЕСТНОЕ ОГРАНИЧЕНИЕ: доступ к `HOST://` требует capability-токены
- **Статус:** ПО ЗАМЫСЛУ
- **Симптом:** файловый менеджер открывает обе панели на `AIOS://` (песочница); переход на `HOST://` показывает пустой список, а операции с хостом падают с `denied: missing capability`

### ИЗВЕСТНОЕ ОГРАНИЧЕНИЕ: enforcement подписанных манифестов опционален через env
- **Статус:** ПО ЗАМЫСЛУ
- **Симптом:** `store install` / `store update` отклоняют неподписанные или недоверенные блоки, когда задан `AIOS_TRUSTED_PUBLIC_KEYS` (или `trusted_public_keys` источника), хотя та же установка без него проходит
- **Обходной путь:** задавайте `AIOS_TRUSTED_PUBLIC_KEYS` только на системах, где нужны только проверенные установки; оставьте его пустым (по умолчанию), чтобы разрешить неподписанные блоки, сохранив проверку подписи по встроенному ключу
- **Примечание:** путь `store publish` через мост использует `BlockInstaller::from_env` (учитывает `AIOS_TRUSTED_PUBLIC_KEYS`), поэтому *подписанная* публикация ограничена локальной политикой доверия, а *неподписанные* публикации остаются разрешёнными, пока не настроены доверенные ключи (см. `docs/ARCHITECTURE.md`, Фаза 42)

### ИЗВЕСТНОЕ ОГРАНИЧЕНИЕ: `store publish` требует работающий сервис обновлений
- **Статус:** ПО ЗАМЫСЛУ
- **Симптом:** `store publish <file.wasm>` падает с ошибкой соединения, когда на `AIOS_BRIDGE_PORT` (по умолчанию `8080`) не слушает сервер моста

- **Примечание:** wasm-нагрузка кодируется в base64 и проверяется по вычисленному SHA-256 на сервере перед установкой

### ИЗВЕСТНОЕ ОГРАНИЧЕНИЕ: удалённые источники Store требуют сеть
- **Статус:** ПО ЗАМЫСЛУ
- **Симптом:** `store search` / `store install` / `store update` против GitHub или HTTP-источника падают с ошибкой скачивания, когда нет сети или удалённый сервис недоступен

- **Примечание:** бинарники блоков проверяются по SHA-256 из манифеста при установке; подделанный payload отклоняется с ошибкой контрольной суммы

### ИЗВЕСТНОЕ ОГРАНИЧЕНИЕ: вкладка Web в TUI отображает только текст
- **Статус:** ПО ЗАМЫСЛУ
- **Симптом:** терминальная вкладка Web не может рендерить CSS/JS/изображения — страницы показываются как структурированный текст (заголовки `#`, списки `•`/`1.`, таблицы `|`, `hr`, изображения как `[alt]`)
- **Примечание:** это внутреннее ограничение терминала, а не регрессия. Для полноценного браузинга используйте нативный браузер: нажмите `W` в любом TUI или откройте вкладку GUI **Browser** (F7)
- **Примечание (v2.17.0):** для JS-тяжёлых сайтов текстовый вид переключается на headless-рендер класса Chromium (`--dump-dom`), когда обычная загрузка не даёт читаемого текста. Требуется установленный доступный браузер класса Chromium (`msedge`/`chromium`/`google-chrome`); бинарник переопределяется через `AIOS_HEADLESS_BROWSER`, `--no-sandbox` (контейнеры) — через `AIOS_HEADLESS_NO_SANDBOX=1`. Без браузера страница показывается как загружена.

### ИЗВЕСТНОЕ ОГРАНИЧЕНИЕ: лог чата AI Console — один JSONL-файл без ротации
- **Статус:** ПО ЗАМЫСЛУ

- **Примечание:** файл читается построчно, поэтому повреждённая последняя строка не ломает запуск

### BUG-010: Ранний выход из `schedule_next` мешает корректному поведению aging
- **Статус:** ИСПРАВЛЕНО (v0.4.0)
- **Симптом:** `test_scheduler_aging_starvation_prevention` падает — процесс с низким приоритетом и boost aging не выбирается вместо процесса с высоким приоритетом
- **Причина:** Внутренний цикл `schedule_next()` содержал `break` после нахождения первого готового процесса в каждой очереди приоритетов. Из-за aging более поздний процесс в очереди мог иметь более высокий эффективный приоритет, но `break` не позволял проверить всех кандидатов.
- **Исправление:** `break` убран, теперь проверяются все готовые процессы в очереди. Выбирается кандидат с наибольшим эффективным приоритетом.
- **Затронутый файл:** `aios-process-mgr/src/scheduler.rs:320`

### BUG-011: Нестабильные тесты графа зависимостей из-за недетерминированной топологической сортировки
- **Статус:** ИСПРАВЛЕНО (v0.4.0)
- **Симптом:** `test_unload_order_reversed` и `test_block_dependency_graph_ordering` падают с интермитентными ошибками
- **Причина:** Алгоритм Кана обрабатывает узлы через `VecDeque`, инициированный из `HashMap`, что недетерминировано. Независимые узлы (без зависимостей друг от друга) могут появиться в любом порядке. Тесты предполагали фиксированный порядок.
- **Исправление:** Тесты изменены так, чтобы проверялись только ограничения зависимостей (если X зависит от Y, то Y появляется перед X в порядке загрузки), а не абсолютные позиции независимых узлов.
- **Затронутые файлы:** `aios-block-mgr/src/dependency.rs:225-236`, `tests/integration_test.rs`

## Потенциальные будущие проблемы

### RISK-001: Переполнение packet_id в AtomicU64
- **Описание:** `PACKET_COUNTER` в ipc_protocol.rs — это `AtomicU64`, который переполнится после 2^64 пакетов
- **Влияние:** Практически невозможно (потребуются годы при высокой пропускной способности)
- **Меры:** В настоящее время не обрабатывается; можно добавить логику wrapping_add или сброс

### RISK-002: Не рекурсивный поиск `find_by_name`
- **Описание:** `BlockRegistry::find_by_name` выполняет линейный поиск по всем записям
- **Влияние:** O(n) на каждый поиск; пренебрежимо на текущем масштабе, но может стать проблемой при тысячах блоков
- **Меры:** Можно добавить вторичный индекс HashMap по имени -> id

### RISK-003: Отсутствие выгрузки блока во время активного hot-swap
- **Описание:** `BlockLoader::unload_block` выводит предупреждение, но не запрещает выгрузку активного блока
- **Влияние:** Сообщения IPC в процессе обработки могут быть адресованы удалённому блоку
- **Меры:** В продакшене активные блоки должны замораживаться перед выгрузкой

### RISK-004: Watchdog не интегрирован с потоком оркестратора
- **Статус:** ИСПРАВЛЕНО (v0.3.0)
- **Описание:** Кrate watchdog был реализован, но не подключён к потоку AI Orchestrator в main.rs
- **Исправление:** Поток heartbeat watchdog теперь работает в фоне во время сессии TUI; заголовок dashboard отображает актуальное состояние watchdog
- **Затронутые файлы:** `aios-tui/src/main.rs`, `aios-tui/src/dashboard.rs`

### RISK-005: WebView работает в фоновом потоке — несовместимо с macOS
- **Описание:** `WebBrowser` в `aios-webview` запускает цикл событий winit в фоновом потоке; на macOS winit/wry требуют цикл событий в главном потоке
- **Влияние:** Окно браузера не откроется в сборках для macOS

- **Тесты:** `test_epoch_timeout_interrupts_runaway_wasm` (бесконечный цикл прерывается за ~150 мс при топливе, которого хватило бы на ~10 с) и `test_epoch_deadline_rearmed_between_calls`
- **Затронутые файлы:** `aios-wasm/src/sandbox.rs`, `aios-wasm/src/executor.rs`

### BUG-039: падение GUI/TUI при определении железа — индекс CSV `wmic` за границей
- **Статус:** ИСПРАВЛЕНО (v2.9.1)
- **Симптом:** `aios-gui` (и любой бинарник, вызывающий `HardwareProfile::detect`) падал при старте с `index out of bounds: the len is 2 but the index is 2` в `aios-hal/src/hardware.rs` — окно GUI не открывалось
- **Причина:** `detect_memory` разбирал `wmic memorychip get Capacity,Speed,DimmLocator /format:csv`, обращаясь к `parts[2]` после проверки только `parts.len() >= 2`; на машинах, где wmic выдаёт короткие строки (например, пустая колонка Speed схлопывается в строку из 2 полей), обращение по индексу паниковало
- **Исправление:** разбор вынесен в чистый помощник `HardwareProfile::parse_wmic_memory_csv`, требующий `parts.len() >= 3` (Node + Capacity + Speed) до обращения к любому индексу; повреждённые/короткие строки пропускаются вместо падения
- **Тесты:** `test_parse_wmic_memory_csv_full_rows` (две DIMM суммируются, скорость читается) и `test_parse_wmic_memory_csv_short_rows_no_panic` (короткая строка из 2 полей пропускается, валидная всё ещё разбирается)
- **Затронутые файлы:** `aios-hal/src/hardware.rs`

### BUG-040: `grub-install` падал с exit 127 в окружении live-установщика
- **Статус:** ИСПРАВЛЕНО (v2.33.0)
- **Симптом:** установщик копировал корневую ФС на целевой диск, затем погибал на
  `grub-install` с `exitcode=0x00000100`/`0x7f`; kernel panic «Attempted to kill init».
- **Причина:** бинарник Alpine `grub-install` слинкован с `liblzma.so.5` и
  `libdevmapper.so.1.02` (пакеты `xz-libs` и `device-mapper-libs`); когда в образе
  были только бинарники `xz`/`lvm2`, динамический линковщик отказывался запускать
  бинарник (exit 127). Ядро позже подгружает модуль `dm` по требованию.
- **Исправление:** в initramfs добавлены `xz-libs` и `device-mapper-libs`;
  grub-install для i386-pc и x86_64-efi теперь выходит с 0. Добавлена диагностика
  на основе `ldd` в отладочном пути сборки (`AIOS_DBG=1`), а stderr grub-install
  сохраняется в `/mnt/target/grub-err.txt`.
- **Затронутые файлы:** инструменты сборки (список пакетов initramfs), `live/aios-install`

### BUG-041: sfdisk отвергает имена GPT-типов с пробелом (`type=BIOS boot`)

### BUG-042: heredoc с кавычками оставил `${DEV}` литералом в grub.cfg → `root=3`
- **Статус:** ИСПРАВЛЕНО (v2.33.0)
- **Симптом:** установленная система не загружалась: kernel panic
  `VFS: Unable to mount root fs on "3" or unknown-block(0,3)`.
- **Причина:** grub.cfg генерировался heredoc-блоком с кавычками (`cat <<'GRUB'`),
  поэтому `${DEV}` оставался литералом в файле; GRUB затем подставлял свою
  (пустую) переменную `${DEV}`, превращая `root=${DEV}3` в `root=3`.
- **Исправление:** heredoc без кавычек (`<<GRUB`), чтобы шелл раскрыл `${DEV}`
  до того, как файл прочитает GRUB.
- **Затронутые файлы:** `live/aios-install`

### BUG-043: GRUB не может встроить BIOS core.img на GPT без BIOS Boot-раздела
- **Статус:** ИЗВЕСТНОЕ ОГРАНИЧЕНИЕ, обработано (v2.33.0)
- **Симптом:** `grub-install --target=i386-pc` предупреждал `this GPT partition
  label contains no BIOS Boot Partition; embedding won't be possible` и выходил с 1.
- **Причина:** на GPT-дисках GRUB BIOS некуда встраивать `core.img` (зазор после
  MBR непригоден для GPT-раскладки без отдельного раздела).
- **Обход:** установщик создаёт выделенный BIOS boot-раздел 1 МиБ (GUID
  `21686148-...`) первым, чтобы встраивание для BIOS работало. UEFI-загрузка не
  затрагивается (используется EFI System Partition).

### BUG-044: RAW-дискриминатор — GP#13 на реальном железе доказывает коррупцию IDT-гейта вектора-32 (PIT IRQ0)
- **Статус:** ПОДТВЕРЖДЁН на реальном железе байт-истиной (v0.5.1)
- **Симптом:** при загрузке с записанной сырыми байтами USB-флешки ядро дошло
  до probe-блока, напечатало RAW-дамп гейтов IDT, после чего намеренный мягкий
  `int 0x20` вызвал #GP (General Protection Fault, vector-13) по не-каноническому адресу `ip=0xffffffff000aa2`.
- **Байт-доказательства:**
  - свежий ISO записан на флешку сырыми байтами, read-back „mism=0“, содержит
    маркеры IDT-RAW-32 и IDT-RAW-50 (RAW=True в реально загруженном образе);
  - вектор-50 (мягкий мягкий INT, используемый probe планировщика) — цел;
  - offset гейта вектора-32 повреждён:  x000aa2 + upper=0xffffffff вместо
    адреса линковки  xffffffff8000xxxx — средние 16 бит offset обработчика
    обнулены, поэтому мягкий INT в вектор-32 уходит по не-каноническому адресу
    и срабатывает #GP (#GP13).
- **Предполагаемая корневая причина (ждёт фикса):** дескриптор гейта IDT для
  вектора-32 коррумпируется при установке — offset_mid (биты 16..31 адреса
  обработчика) обнулён при корректном offset_high=0xffffffff. Вектор-50
  строится отдельным путём и цел; дискриминатор доказал, что порча именно в
  сырых байтах гейта, а не в ISO/limine/загрузчике.
- **Направление фикса:** укрепить/принудительно чинить установку гейта вектора-32
  в ios-kernel/src/interrupts/idt.rs (set_handler/set_gate), чтобы offset_mid
  всегда брался из полного 64-битного обработчика (биты 16..31), а не усекался;
  затем перепроверить через дискриминатор RAW.
- **Затронутые файлы:** ios-kernel/src/interrupts/idt.rs (установка гейта),
  ios-kernel-run/src/main.rs (probe).
